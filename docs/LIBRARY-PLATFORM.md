# Library Platform — Architecture (for review, not implemented)

A single engine that renders every SAP book in Project NEO. Adding a book means
adding data. It must never mean adding React.

Status: **design only**. Nothing here is built yet.

---

## 1. The problem this replaces

Today a book is described in four places that were built at different times and
have never been reconciled by anything but a script written after the fact:

| source | knows | used by |
|---|---|---|
| `data/library.ts` | title, page count, chapter list | the shelf |
| `data/library/N-full.json` | title, pages, chapters, sections | the reader |
| `data/library/N-index.json` | flat section index | search |
| `data/ai-tree/N.json` | chapters → sections | Ask AI |

Consequences already measured:

- The AI tree labelled chapters with their first *section's* title, so the reader
  said "Configuring Generic Functions" and the AI said "Object Information" for
  the same chapter. 89 of 134 chapters were affected.
- `book8` stores headings as `{titleEn, titleHe}`; the other ten use
  `{title, he}`. Every consumer that assumed one schema silently lost data —
  including my own first audit, which reported "0% Hebrew" for a book that is
  fully translated.
- `book8` has a bespoke 244-line page component. Every other book shares
  `BookReader`.
- Colour/identity lived nowhere, so eleven shelf cards looked interchangeable.

The through-line: **there is no single definition of what a book is.** Each
surface invented its own. The fix is not to patch the surfaces — it is to make
one definition that all of them are forced to read.

---

## 2. Principles

1. **One schema.** A book is one object. Everything else is derived.
2. **Data in, no code.** Adding a book = adding one JSON file + one registry row.
3. **Derived, never duplicated.** Search index, AI tree and shelf card are
   *generated* from the book, never authored alongside it.
4. **Validation is a build gate,** not a script someone remembers to run.
5. **Identity by module, content by book.** Two PM books share colour, badge and
   iconography. They share nothing else — not chapters, not content, not page
   counts. (This is the rule that keeps a config guide and a business-user guide
   visually related but editorially independent.)
6. **Variants are declared, not special-cased.** A Fiori app catalogue is not a
   narrative book. The schema says so; the renderer adapts. No `if (book7)`.

## 3. The schema

One file per book: `data/books/<bookId>.json`.

```jsonc
{
  "id": "book9",
  "schemaVersion": 1,

  "meta": {
    "title":   { "en": "Plant Maintenance with SAP S/4HANA: Business User Guide",
                 "he": "אחזקת מפעל ב-SAP S/4HANA — מדריך למשתמש העסקי" },
    "module":  "PM",                    // drives colour, badge, icon
    "kind":    "business-user",         // drives shelf grouping
    "structure": "narrative",           // narrative | catalogue | reference
    "publisher": "SAP PRESS",
    "pages": 669,
    "year": 2023,
    "summary": { "en": "…", "he": "…" }
  },

  "chapters": [
    {
      "n": 1,
      "title": { "en": "Introduction to Plant Maintenance", "he": "מבוא לאחזקת מפעל" },
      "startPage": 21,
      "sections": [
        {
          "id": "1.1",                          // unique WITHIN the book
          "title": { "en": "…", "he": "…" },
          "page": 23,
          "body": "…",                          // full text, reader + retrieval
          "figures": ["fig-1-1"]                // optional
        }
      ]
    }
  ]
}
```

### Why this shape

- **Bilingual is structural, not optional.** `{en, he}` everywhere removes the
  `title`/`he` vs `titleEn`/`titleHe` divergence permanently. There is one way to
  express a heading.
- **`structure`** is what lets book7 stop being an exception. A `catalogue`
  declares that its section ids are external codes (Fiori app ids), that the same
  entry may legitimately appear under two chapters, and that numbering is not
  hierarchical. The validator and the renderer both read this field instead of
  hard-coding a book number.
- **`schemaVersion`** so a future migration is mechanical.
- **Section `id` is unique within the book, not globally.** The addressable key
  everywhere is `bookId#chapter#section` — already the citation format the AI
  emits, so nothing changes downstream.

## 4. Derived artefacts

Generated by `scripts/build-library.mjs`. Never hand-edited. Regenerated in CI.

```
data/books/<bookId>.json          ← the ONLY authored file
        │
        ├─→ data/derived/shelf.json        cards: title, module, pages, chapters, cover
        ├─→ data/derived/search.json       flat sections for the palette
        ├─→ data/derived/ai-tree/<id>.json chapters → sections, for Ask AI
        └─→ data/derived/manifest.json     counts + checksums for validation
```

Two properties matter more than the file list:

- **A derived artefact can never disagree with the book**, because it has no
  independent existence. The chapter-title defect is not fixed here — it is made
  unrepresentable.
- **Lazy loading survives.** Per-book AI tree files stay split (book7 alone is
  1,689 sections / 160 KB); the shelf index stays tiny and eager.

## 5. Identity

`lib/book-identity.ts` (already built) keys colour to **module**, not to book.

| module | accent | contrast on white |
|---|---|---|
| PM | `#d62027` | 5.13 |
| PP | `#b91c1c` | 6.47 |
| PP-PI | `#9f1239` | 8.02 |
| PP/DS | `#7c3aed` | 5.70 |
| QM | `#047857` | 5.48 |
| MM | `#1d4ed8` | 6.70 |
| EWM | `#c2410c` | 5.18 |
| S&OP | `#0e7490` | 5.36 |
| Fiori | `#a21caf` | 6.32 |
| S/4HANA | `#57534e` | 7.63 |

All pass WCAG AA for body text, so they are safe as title colours.

**This is what makes book1 and book9 correct.** Both are PM, so both carry the
same red, the same `PM` badge, the same icon — a user sees they are siblings.
Their `kind` differs (`configuration` vs `business-user`), so they sit in
different shelf groups with different cover treatments, and their content is
entirely independent. Shared identity, independent data.

## 6. The rendering engine

One component tree. No per-book components. No `book8/page.tsx`.

```
app/library/[bookId]/page.tsx        generateStaticParams over the registry
  └── <BookShell book>               header, progress, mode switch
        ├── <BookHeader>             cover, title, module badge, pages, chapters
        ├── <BookNav>                chapters → sections (shared with Ask AI)
        └── <BookContent>
              ├── <ChapterView>      narrative
              └── <CatalogueView>    structure: "catalogue"
```

`structure` selects the content view. That is the *only* branch, it is driven by
data, and adding a third structure means adding one view — not touching the ten
books that already work.

**What this deletes:** `app/library/book1..book11/page.tsx` (eleven files,
including book8's bespoke 244 lines) collapse into one dynamic route.

---

## 7. Ask AI integration

Ask AI stops maintaining its own map. It reads the same registry and the same
derived tree, so:

- the scope tree shows the same chapter titles as the reader, by construction
- a citation resolves through the same `bookId#chapter#section` key
- the active book's module accent tints the AI surface — the visual continuity
  between the shelf and the chat comes free, because both read one identity

## 8. Validation as a gate

`npm run audit:library` and `audit:tree` become one `validate-library.mjs`, run
in CI and failing the build on:

| rule | severity |
|---|---|
| schema does not match `schemaVersion` | error |
| chapter numbers non-contiguous or unordered | error |
| section filed under the wrong chapter (`narrative` only) | error |
| duplicate section id with differing titles | error |
| missing Hebrew title | error |
| derived artefact out of date vs source checksum | error |
| duplicate section id, identical title, `catalogue` | info |
| near-identical dataset to another book (≥90% shared ids) | **report** |
| section numbering gap | warning |

That second-to-last rule is how `book8` gets handled: the platform *reports* that
two datasets overlap 271/271 and shows the evidence. It does not delete, merge or
decide. You decide, later, with the report in hand.

---

## 9. Adding a future book

1. Write `data/books/book12.json`.
2. Add one row to the identity registry (module + kind).
3. `npm run build`.

No component. No route. No parser. No exception. If step 3 fails, the validator
says exactly which rule was broken.

---

## 10. Migration path

Non-destructive, reversible, and no content is rewritten by hand.

| phase | action | risk |
|---|---|---|
| 1 | Write the schema + validator. Nothing renders from it yet. | none |
| 2 | `migrate-books.mjs` converts all 11 sources → `data/books/*.json`. Both schemas read; output normalised. | none — additive |
| 3 | Validator runs over the migrated set. Fix what it finds. | none |
| 4 | Build the engine behind `/library/v2/[bookId]`. Old routes untouched. | none |
| 5 | Compare v2 against every existing book route. | none |
| 6 | Swap routes, delete the eleven page files. | reversible |

Phases 1–5 change nothing a user can see.

## 11. Open questions for you

1. **`body` in the book file** makes one book7 file ~4 MB. Alternative: keep
   `body` in per-chapter shards and reference them. Adds a file layer; keeps
   authoring simpler. Which do you prefer?
2. **`kind` taxonomy** — proposed: `sap-press`, `configuration`, `business-user`,
   `reference`, `foundation`, `academy`. Your earlier list also had ZaranTech and
   Technical Books. Confirm the final set.
3. **Reading progress** — per section or per chapter? Affects the schema.
4. **book8** stays untouched until you decide. Under this platform it is simply
   a dataset that the report flags.
