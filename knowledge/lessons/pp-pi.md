# לקחים — PP / PP-PI

<div dir="rtl">

לקחים מבוססי ניסיון SAP סטנדרטי (curated). כל לקח: `[מודול / אובייקט / סימפטום] שורש → תיקון שעבד (הימנע מ: X). best practice`.

- [PP-PI / Control Recipe / לא נשלח ל-MES] כשה-control recipe לא מגיע ל-MES, השורש כמעט תמיד destination לא מוגדר או ממשק PI-PO down — בדוק CO53 לפני שמאשימים את ה-order עצמו. (הימנע מ: יצירת ה-order מחדש — לא פותר את הממשק). best practice: הגדר control recipe destination ובדוק אותו כחלק מ-go-live.
- [PP-PI / COR6N / over-delivery בעת אישור] tolerance לא מוגדר או כמות שגויה — הגדר under/over-delivery tolerance ב-material/order מראש. (הימנע מ: ביטול ה-order). 
- [PP-PI / COGI / חוסר רכיב חוזר] backflush נכשל כי הרכיב לא סופק ל-production storage location — תזמן staging לפני האישור. (הימנע מ: post ידני חוזר ב-COGI בלי לתקן את ה-staging — הבעיה תחזור).
- [PP / Production Order / שחרור נכשל] missing parts הוא הגורם השכיח — בדוק CO24 לפני שינוי scope of check. הרחבת scope כדי "לעקוף" מסתירה בעיית אספקה אמיתית.
- [PP-PI / Batch determination / נכשל בעת release] אסטרטגיית batch/classification לא הושלמה — השלם CU50/determination ב-customizing לפני production. (הימנע מ: הזנת batch ידנית כפתרון קבע).
- [PP / Production Version / order לא נוצר] גרסת ייצור לא תקפה לתאריך — תחזק production version (C223/MM02 MRP4) עם תוקף נכון; טעות תוקף חוזרת בכל MRP run.
- best practice כללי: ב-PP-PI כל תקלת אישור/backflush מתחילה בבדיקת **status הפאזה** ו-**זמינות הרכיב** — שני אלה מסבירים את רוב המקרים לפני חפירה עמוקה.
- [PP-PI / COGI / "הזן סדרה" והאצווה כשירה] כשהאצווה משוחררת, מסווגת ובתוקף ויש מלאי באתר האחסון — הקביעה **לא רצה**, היא לא נכשלה. השורש הוא חוסר **רשומת אסטרטגיית חיפוש** למקט. (הימנע מ: שיבוץ ידני חוזר בכל דיווח — מעקף לשורה בודדת שלא מונע את הבא). אבחון מכריע: COR2/CO02 → רכיבים → קביעת סדרה; "לא נמצאה אסטרטגיית חיפוש" מול "לא נמצאה אצווה" מפריד בין קונפיג למלאי.
- [PP-PI / Batch Determination / הוגדר אבל לא עובד] קביעת סדרה אוטומטית דורשת רשומה **בשני מקומות נפרדים**: MBC1/MBC2/MBC3 (סוג אסטרטגיה ZME2, לפי סוג תנועה 261 + אתר + מקט) **וגם** COB1/COB2/COB3 (סוג אסטרטגיה CO01, לפי סוג הזמנה + אתר + מקט). הגדרה באחד בלבד לא מפעילה את הקביעה. (הימנע מ: להסיק "מוגדר" אחרי בדיקת טרנזקציה אחת).
- [PP-PI / Batch Determination / איתור מקטים שנשמטו] השוואה למקטים **שכנים באותה סדרת מספור** ברשימת MBC2/COB2 מזהה פער כיסוי בשניות: אם לשכנים יש רשומה ולמקט אין, הוא נשמט בהקמה. במקרה אמיתי (07.2026, מקט 1218184) בדיוק כך אותר השורש. ראה `../cases/2026-07-cogi-enter-batch-missing-strategy.md`.
- [PP-PI / COGI / סדרה בשיבוץ ידני] כשמשבצים אצווה ידנית — לבחור **לפי תוקף (FEFO)** ולא שרירותית, אחרת נשרפות אצוות שהיו צריכות לצאת ראשונות.
- [PP-PI / COGI / מחיקת שורה] מחיקה (גם עם ספירת מלאי) מיישרת **מלאי בלבד** ולא מחזירה **עלות לפקודה**. לרכיב שנצרך בפועל — תמיד תיקון השורש + עיבוד מחדש; מחיקה שמורה רק לשורות שלא נצרכו.
- [PP / Backflush כפול / "מסמך חומר לא ניתן לעיבוד"] כשאותה צריכה נרשמה פעמיים (שני מסמכי חומר), ו-MIGO מסרב לבטל עם "מסמך חומר לא ניתן לעיבוד" — המסמך נוצר מדיווח ייצור, ולכן מבטלים את **הדיווח ב-CO13**, לא ב-MIGO. (הימנע מ: לבטל את שני המסמכים — צריכה אחת אמיתית חייבת להישאר). דורש קודם **ביטול TECO** (CO02 → הגבל עיבוד → בטל סגירה טכנית) ורישום בתקופה פתוחה. ראה `../cases/2026-08-cogi-double-backflush-teco-plant0001.md`.
- [PP / COGI / תקופה סגורה] "רישום אפשרי רק בתקופות X ו-Y" = צריכות מתקופות סגורות. הטיפול (שינוי תאריך רישום לתקופה פתוחה + עיבוד מחדש, או מחיקה+ספירה) הוא **בתיאום הכספים** (MMRV/OB52 בבעלותם), לא לבד.
